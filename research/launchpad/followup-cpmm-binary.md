## RECOMMENDATIONS
- Building the graduation-pool CPI against the raydium-cpmm-cpi anchor-0.30.1 branch is SAFE for plain initialize as of 2026-08-08: discriminator, 3 u64 args, and the 20-account list (order/writable/signer/fee-receiver address) are byte-identical to the deployed binary and have been stable since 2024-08-30. Per the team's doctrine, still prove it in bankrun against a FRESH mainnet dump of CPMMoo8L3F4NbTegBCKVNunggL7H1ZpdTHKxQB5qKP1C taken at slot >= 425801539 (the committed fixture must post-date 2026-06-11), plus dumps of AmmConfig D4FPEruK... and the DNXge fee-receiver token account.
- Treat the 0.30.1 crate's structs as wire-compatible but semantically stale: if any launchpad code reads AmmConfig.creator_fee_rate, PoolState.enable_creator_fee/creator_fees_token_*, or PoolState.recent_epoch, vendor the struct with creator_fee_rate:u64 at offset 108 (padding [u64;15]) — or lift types from the raydium-cpi anchor-0.32.1 branch — rather than trusting the 0.30.1 padding fields.
- Do not design tokenomics around CPMM creator fees: pools created via permissionless initialize get enable_creator_fee=false hardwired, so config 0's creatorFeeRate=500 never taxes their swaps and collect_creator_fee yields nothing; the creator-fee path (initialize_with_permission) requires a Permission PDA only Raydium's admin can mint. If creator-fee revenue on the graduation pool matters, that's a business-development conversation with Raydium, not a code path.
- Use config index 0 (D4FPEruKEHrG5TenZ2mpDGEfu1iUvTiqBxvpU8HLBvC2, 0.25% trade fee) and budget exactly 0.15 SOL create_pool_fee per graduation (plus rent for pool/lp/vault/observation accounts); indexes 8-18 exist but are high-creator-fee configs hidden from UI and pointless for permissionless pools.
- Account for the open_time clamp in the deployed program: open_time <= current unix time is silently rewritten to now+1, so 'open immediately' is the default behavior and any scheduled-open logic must pass a future timestamp.
- If graduated tokens can be token-2022 with exotic extensions (interest-bearing, scaled-ui-amount beyond the whitelisted set), the deployed binary requires admin-created SupportMintAssociated PDAs passed as remaining_accounts — the 0.30.1 CPI crate cannot express this; for plain SPL-token launches this is a non-issue. Decide the launchpad's mint-extension policy accordingly.
- The program is upgradeable (Squads multisig authority FytDrVz..., upgraded roughly quarterly: 2025-08-18, 2025-10-31, 2025-12-29, 2026-06-11). Add a pre-release and periodic check comparing the ProgramData slot field against the pinned 425801539 so an unnoticed upgrade can't silently invalidate the verified interface — same failure mode as the spl-governance fork burn.
- Trust the on-chain IDL for initialize/swaps/AmmConfig but not as a complete instruction inventory (it's missing the two support-mint admin instructions present in the binary); when the team needs ground truth for anything new, repeat the binary-string / parsed-transaction verification used here rather than solscan (which 403s from datacenter IPs) or repo master (which now leads the deployment only by commit-push lag, but has historically been pushed AFTER mainnet deploys).
